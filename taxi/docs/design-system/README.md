# Taxi Design System

Нормативная документация дизайн-системы. Структура повторяет общепринятое деление: Concept → Foundations → Components → Patterns → Templates.

| Документ | Что внутри |
|---|---|
| [`CONCEPT.md`](CONCEPT.md) | принципы, визуальный язык, на чём основаны решения |
| [`FOUNDATIONS.md`](FOUNDATIONS.md) | цвет, типографика, пространство, форма, движение, слои, брейкпоинты |
| [`ACCESSIBILITY.md`](ACCESSIBILITY.md) | требования доступности и как они проверяются автоматически |
| [`CONTRAST_MATRIX.md`](CONTRAST_MATRIX.md) | матрица контраста — генерируется, руками не править |
| [`COMPONENTS.md`](COMPONENTS.md) | инвентарь компонентов, API, варианты, состояния |
| [`PATTERNS.md`](PATTERNS.md) | составные решения: карточка заказа, модалки, карта, формы |
| [`TEMPLATES.md`](TEMPLATES.md) | шаблоны экранов и правила компоновки |
| [`CONTRIBUTING.md`](CONTRIBUTING.md) | как вносить изменения, версионирование, порядок ревью |

Реализация и enforcement описаны отдельно: [`../UI_KIT.md`](../UI_KIT.md).

## Статус зрелости

| Слой | Состояние |
|---|---|
| Foundations | реализованы в коде, покрыты автоматическими проверками |
| Accessibility | формализован, роли токенов проверяются машинно |
| Components | задокументированы фактические компоненты; унификация API не завершена |
| Patterns | задокументированы сложившиеся решения; часть требует нормализации |
| Templates | описаны существующие экраны |

Документация описывает систему **как она есть в коде**, а не как её хотелось бы видеть. Там, где фактическое решение расходится с желаемым, это помечено явно — иначе документ перестаёт быть полезным при работе с кодом.
