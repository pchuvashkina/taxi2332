# Accessibility

Целевой уровень — **WCAG 2.1 AA**.

Документ описывает не намерения, а проверяемые требования. Там, где требование сегодня не выполняется, это записано как долг с конкретной формулировкой, а не замолчано.

## Как это проверяется

```bash
npm run lint:a11y              # проверка
npm run lint:a11y -- --report  # перегенерировать матрицу контраста
```

Скрипт `scripts/check-contrast.mjs` считает контраст каждого семантического токена против всех поверхностей и падает, если токен не выполняет обещание своей роли. Роли заданы в секции `a11y` файла `tokens.json`.

**Токен без назначенной роли — тоже ошибка.** Добавить цвет и «забыть» классифицировать его нельзя: скрипт перечислит такие токены и завершится с ненулевым кодом. Это и есть формализация: контраст перестал быть разовым замером в отчёте и стал условием сборки.

Актуальные числа — в [`CONTRAST_MATRIX.md`](CONTRAST_MATRIX.md), файл генерируется.

## Роли токенов

| Роль | Требование | Где применять |
|---|---|---|
| `surface` | — | фон, относительно которого считается контраст |
| `text` | ≥ 4.5:1 | обычный текст любого размера |
| `text-large` | ≥ 3:1 | крупный текст: ≥ 24px либо ≥ 18.66px полужирный |
| `non-text` | ≥ 3:1 | значимые иконки, границы полей ввода, индикаторы состояния |
| `fill` | не нормируется | заливка-подложка; **цвет не должен быть единственным носителем смысла** |
| `decorative` | — | декор и неактивные (disabled) элементы — WCAG их не нормирует |

Поверхности, против которых считается контраст: `--c-surface`, `--c-surface-canvas`, `--c-surface-subtle`. Токен обязан выполнять требование против **худшей** из них, а не против удобной.

### Почему у части токенов роль `fill`

Девять токенов — `secondary`, `warning`, `warning-strong`, `warning-vivid`, `success-alt`, `success-vivid`, `accent-light`, `status-pickup`, `status-dropoff` — не дотягивают до 3:1 на белом фоне. Это цвета исторической айдентики продукта, и менять их — решение заказчика, а не следствие рефакторинга.

Вместо подмены цвета зафиксировано ограничение: **этими токенами нельзя передавать информацию цветом**. Жёлтая плашка статуса допустима только с текстовой подписью рядом. Для случаев, где нужен именно текст, у каждого есть парный вариант с контрастом ≥ 4.5:1 — `--c-warning-text`, `--c-success-text`, `--c-secondary-text`, `--c-accent-text` и другие.

Это соответствие WCAG 1.4.1 (Use of Color) при сохранении айдентики.

## Требования сверх контраста

### Цвет не единственный носитель смысла (1.4.1)

Любое состояние — статус заказа, ошибка поля, успех операции — дублируется текстом или иконкой. Проверяется при ревью, автоматизации нет.

### Фокус (2.4.7)

Интерактивные элементы обязаны иметь видимую индикацию фокуса. Удаление `outline` без замены — ошибка ревью.

### Размер цели (2.5.5, уровень AAA, взят как ориентир)

Минимальная область нажатия — 44×44 px. Для плотных элементов допустимо увеличение области через `padding` или псевдоэлемент при меньшем визуальном размере.

### Движение (2.3.3)

Приложение уважает `prefers-reduced-motion`: длительности переключаются на `--d-instant`. Анимаций с частотой вспышек выше 3 Гц в системе нет.

### Текстовые альтернативы (1.1.1)

Декоративные изображения — `alt=""`. Значимые иконки — `aria-label`. Пример корректной реализации: `CarClassBadge`, где изображение имеет пустой `alt`, а смысл передан через `aria-label` контейнера.

## Долги

| ID | Что | Почему не закрыто |
|---|---|---|
| A11Y-01 | Девять токенов не дают 3:1 как самостоятельные индикаторы | цвета исторической айдентики; смена — решение заказчика. Обойдено правилом роли `fill` |
| A11Y-02 | Нет автоматической проверки фокуса и размера целей | требует прогона в браузере (axe-core в e2e), выходит за рамки статических проверок |
| A11Y-03 | Контраст текста на цветных заливках не проверяется машинно | требует знания фактических пар «фон + текст» из разметки, не выводится из токенов |
| A11Y-04 | Нет проверки на дублирование смысла цветом | проверяется глазами при ревью |

A11Y-02 и A11Y-03 закрываются одним шагом — подключением `axe-core` к существующим Playwright-тестам. Это следующий разумный шаг формализации, но он требует работающей сборки.

## Порядок ручной проверки

При приёмке изменений, затрагивающих цвет или типографику:

1. `npm run lint:a11y` — обязателен, падение блокирует.
2. Проверить статусы заказа: каждый ли сопровождается текстом.
3. Пройти основной сценарий с клавиатуры: виден ли фокус на каждом шаге.
4. Включить в системе сниженную анимацию и убедиться, что переходы не мешают.
5. Проверить карту с несколькими водителями: различимы ли маршруты. Это не требование WCAG, но прямое следствие принципа «цвет должен различать».
